# Events, kiosks, signage, venue maps

- San Juan Bowl micro extracts clone unchanged source shapes with inherited styles and coordinates; its client-loaded Three.js viewer orbits the stack midpoint — why: fused silhouettes must not be invented, and layer spread must not move the camera target.
- San Juan Bowl major-piece exports wrap unchanged detail paths in one named group per piece; viewer lettering assets and exports use the same original shape indices, and micro view is optional — why: grouping and separate lettering selection must preserve approved geometry without duplicating ribbon details.

- San Juan Bowl component assets preserve original top-level SVG drawing order and source coordinates, and count every shape element (path, polygon, polyline — 293 total); `san-juan-logo-measurements.json` records measured geometry and feeds the production calculator — why: exact inspection must not redraw composite shapes or confuse artboard width with badge width.

- Generated map SVG downloads (including ZIP entries) and PDF/PNG inputs pass through `selfContainedSvg` before delivery; SVG logos are nested vector paths with unique IDs, raster images embedded, and missing assets block export — why: Illustrator cannot reliably resolve linked web logos and proofs must not silently lose them. Issued source files remain byte-for-byte unchanged.

- Map previews reuse `PlanZoomFrame` for zoom, pan and an accessible enlarged dialog — why: venue and event pages should share the same inspection controls without altering exports.

- QEII symbol cleanup applies only to the issued QEII floor IDs; imported venues retain every symbol path — why: restroom heads also resemble structural pillar dots.

- Event label patches reuse `venue_map_edits` with scope `event-<eventId>` and floor keys; `qeiiPlanLayout` measures Geist advances and rotated bounds for preview/export — why: text edits do not change shared venue drawings or diverge in SVG downloads.
- SF label defaults resolve through `qeiiFloorMapEdits` in the shared layout and map controls; saved fields override defaults — why: corrected wrapping and turns reach previews and exports without changing venue geometry.

- Designer-supplied SF kiosk CMYK masters (SWOP v2) live in `src/assets/california-kiosks/cmyk/` and are served byte-for-byte via `next-california-kiosk-cmyk-masters.ts` — why: CMYK must never be re-rendered or converted by the app.
- SF kiosk side strips are native faces (`native.faces` + `kioskFaceLayout`), split one object per page from the native PDF and edited by the same editor/export path as the front; strip edits save under `<kiosk>--left|right` — why: one editor and one CMYK export path for every face.
- Legal NEXT signage templates (`legalnext-*` layouts in `src/lib/legal-next-signage-layouts.json`, registry `src/lib/legal-next-signage.ts`) reuse the kiosk layer editor/export via `layout.sign`, kept out of `KIOSK_LIVE_LAYOUTS` (use `liveLayoutById`) — why: one editor/export path, kiosk list stays kiosks only.
- Event agendas and room lists are added in-app (`event_agendas` / `event_rooms`, versioned; publish = admin or brand_lead, enforced by trigger); agenda boards prefer the newest published agenda over the built-in programme, and the SF production status is computed by `assetGates` — why: build users update events without code changes.
- Dark-wall venue sheets (e.g. hotel plans) are tone-flipped for styled map looks by `floorForStyledLook` in `src/lib/venue-floor-normalise.ts`; the issued look keeps the venue inks — why: styled looks map tones by lightness and assumed the QEII light-wall convention.
- Event sign sets: approved `sign_templates` (a base layout id + saved edits + text→fact links) fill `venue_sign_spots` per event into `event_signs`; each built sign's edits live in `kiosk_layer_edits` under `signset:<id>` via the editor's `editKey` prop, and templates only fit spots of the same size (±¼ in) — why: one editor/export path, and artwork is never stretched or reworded with invented facts.
- SF breakout screen surrounds (`sfsurround-*` layouts in `legal-next-signage-layouts.json`, registry `SF_SCREEN_SURROUNDS`) are app-drawn RGB artwork cut to the supplied templates, edited via the sign editor — why: same editor/export path as other signs.
- Venue spot first versions are the generic `divsign-venue-first` template re-flowed per submitted artboard (`divsign-venue-first.<spot8>-<n>of<N>~<w>x<h>`; multi-artboard spots draw one shared ramp across tiers (n=1 bottom) and step lines from `venue-step-guides.ts`, editor id `venue~<spot8>~<sizes>`); rebuild the template with `scripts/venue-first-version-build.py` — why: every new submission gets an editable first version without a per-upload build.
- 3D signs (demo booth, surrounds, pillars, desks, pedestals) are `event_booths` rows with `kind='sign'`; saving a mapped sign face (`signArtTarget` in `booth-art-publish.ts`) pushes its proof to `booth_art` like kiosks; `SIGN_3D` entries stay `pending` (no button) until BoothHub publishes the model — why: booth artwork must come from Element, not BoothHub.
- GlobalLink NEXT SF pillars (`divsign-globallink-pillar-*`) are split from the supplied Canva PDF by `scripts/globallink-pillars-extract.py`: image fills form the ground (stretched past trim via `bgBox`), vectors are pieces, and the headline stays live text turned by a layout-level `rot`, anchored at the middle of its baseline (`align: center`) and set at the designer's type size — why: a retyped name then stays centred where the designer centred it.
- A turned line is measured with `rotatedBox` everywhere (selection, snapping, align tools, print checks, `resizedSignLayout`) and the align tools never change its own `align` — why: it turns about its anchor, so an unturned box or a changed anchor puts it in the wrong place.
- A type size read from a supplied PDF by advance widths is divided by a font build whose widths match the file's embedded font (`public/fonts/Geist-Bold.ttf`, 1.800, for Canva files), never the `fonts-live` 1.3.1 build — why: the two differ on T, X, Y, W, A and V, which skewed every headline by up to 1.85%.
- Supplied multi-line copy is stored as wrapping paragraphs (`LiveText.wrap` box width + `lead`/`align`, joined by `scripts/text-paragraphs.py`; Enter keeps the designer's deliberate breaks) and wrapped by `wrapParagraph` with Geist advances from `geist-advances.json` — why: the editor, print checks and every export must break lines identically.
- The InterContinental SF meeting space (floor plans + capacity chart) comes only from the hotel's supplied fact sheet, transcribed in `src/lib/next-sf-venue-rooms.ts`; it reaches the event room list only as a draft that an admin/brand lead publishes — why: hotel figures are never printed unconfirmed.

- The Master NEXT brand kit (`src/lib/next-brand-kit.ts`, `/events/next/brand-kit`, partner view `/share/next-brand-kit/$token` gated by `get_next_brand_kit_share`) is assembled from existing registries only — why: page, share view and download pack must never drift from the templates and brand guide.
- Cross-surface cascade: curated print-library e-brochures/case studies feed social + print sizes (`/convert?print=<id>`) and slide decks only through `src/lib/print-cascade.ts`, which reads the piece's own copy/figures/hero and never adds numbers — why: one master piece, every surface, no drift or invented figures.
- InterContinental SF floor plans are vector paths split from the hotel's fact sheet by `scripts/sf-venue-floor-vectors.py` into `src/assets/sf-intercontinental/level-N.svg` (shapes and inks as drawn) — why: the sheet's plans are real vectors, so they are never traced or redrawn.
- San Juan Bowl (`san-juan-bowl`) is a built-in event entry with its own data module `src/lib/san-juan-bowl.ts` and brand kit at `/events/san-juan-bowl/brand-kit`; logo files are CDN asset pointers in `src/assets/san-juan-bowl/` from the supplied FINAL_LOGO_26 package — why: venue and dates stay "to be confirmed" until the organisers issue them, and the artwork is never redrawn.

- Booth↔BoothHub pairing lives in `event_booths` (bundled `SF_BOOTH_FALLBACK` is offline-only); saved kiosks push PNG proofs to `booth_art`, served to BoothHub by `/api/public/booths/$event` — why: one list, and 3D always shows the latest saved art.
- Designer-supplied NEXT division templates join the registry only via `src/lib/next-supplied-templates.ts` (live desk files via `DIVISION_LIVE_SIGNS` with a `preview`) — why: the assets listing, division tiles and counts all read `loadNextRegistry()`, so one entry shows everywhere.
- Re-sized signs are their own layout id `<face>~<w>x<h>` (inches), resolved by `liveLayoutById` via `resizedSignLayout` (ground stretched via `native.bgBox`, pieces re-flowed via `LivePart.rx/ry/rs`); artwork files always come from the base id — why: saves, approvals and exports keep working per size without duplicating supplied files.
- New venue spots with artwork are submitted from the event page (`VenueAssetSubmissions`) into `venue_sign_spots` (live file in private `venue-artwork` bucket, artboards read from the file, AI brief in `review`); artboard sizes never fill `w_in/h_in` — why: sizes come only from the site survey.
- Outside-designer files follow one layout, naming rule and version in `src/lib/next-designer-pack.ts` (ZIP, guide PDF, vendor packs read it) — why: every hand-off surface must match.
- Event floor maps are edited only at `/events/next/maps/$eventId`; other pages show them read-only with `EventMapView`, drawn by `src/lib/event-floor-plan.ts` — why: two map editors drifted apart.
- LegalNEXT New York (`legalnext-new-york`, Sheraton New York Times Square) is a started event; its second floor is vector paths split from the hotel PDF by `scripts/sheraton-nyc-floor-vectors.py` (printed glyphs dropped, room names re-set as live labels), and room uses come only from the supplied LegalNEXT venue map — why: same rules as SF, nothing traced or invented.
- The GlobalLink NEXT VIP dinner invitation (`divsign-globallink-vip-dinner`) is split from the supplied Canva PDF by `scripts/next-vip-dinner-extract.py` (reuses the pillar splitter; small images stay pieces, overlapping objects are never merged) — why: the script lettering, NEXT lockup and venue logo must each move or swap on their own while the copy stays live.
